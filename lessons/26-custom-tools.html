写自己的工具Custom Tools

给 agent 加一件你自己的工具有两条路：最简单的是用 FunctionTool 包装一个普通函数；要更精细的控制则继承 ToolBase。

There are two ways to give an agent a tool of your own: the simplest is to wrap a plain function with FunctionTool; for finer control you subclass ToolBase.

🧩 生活类比🧩 Analogy
像往工具箱里自制一件工具：贴上清楚的标签（类型注解 + docstring），助手就知道它叫什么、要什么参数、什么时候用。
Like making your own tool for the box: put a clear label on it (type hints + docstring) and the assistant knows its name, its arguments, and when to use it.

方式一：包装一个函数（推荐）

Option 1: wrap a function (recommended)

方式二：继承 ToolBase

Option 2: subclass ToolBase

需要自定义权限、流式输出或有状态行为时，继承 ToolBase：设置 name / description，实现 __call__，并实现抽象方法 check_permissions（与权限系统对接，第 16 课）。返回值统一为 ToolResponse（或流式 ToolChunk）。

When you need custom permissions, streaming, or stateful behavior, subclass ToolBase: set name / description, implement __call__, and implement the abstract check_permissions (it ties into the permission system, lesson 16). Results are ToolResponse (or streaming ToolChunk).

⚠️ 重要⚠️ Important
错误语义很关键：工具里抛出 AgentOrientedException（如内置的 ToolNotFoundError）会把错误作为工具结果回喂给模型，让 agent 有机会自行纠错；而 DeveloperOrientedException 会向上抛给开发者。据此选择：可恢复的错误用前者，编程 / 配置错误用后者。
Error semantics matter: raising an AgentOrientedException (e.g. the built-in ToolNotFoundError) feeds the error back to the model as a tool result so the agent can recover, whereas a DeveloperOrientedException propagates to the developer. Choose accordingly: recoverable errors → the former, programming/config errors → the latter.

✅ 关键要点✅ Key takeaways
  • 最简路径：FunctionTool(your_function)。Simplest path: FunctionTool(your_function).
  • 类型注解 + docstring 决定模型看到的工具说明。Type hints + docstring define the tool spec the model sees.
  • 进阶：继承 ToolBase，实现 __call__ 与 check_permissions。Advanced: subclass ToolBase, implement __call__ and check_permissions.
